# quantumforge

RAG-система для поиска ответов по вселенной сериала со ссылками на источники.

Учебный проект. Реализует полный RAG-пайплайн: от загрузки исходных документов
до ответа на вопрос со ссылкой на источник.

## Задача

Корпус — материалы по вселенной сериала: описания серий, персонажей, событий
и связей между ними. Материалы взяты с вики.

Полнотекстовый поиск здесь работает плохо, потому что ищет по ключевым словам,
а не по смыслу. Вопрос «кто предал главного героя» не найдёт фрагмент, где написано
«нанёс удар в спину своему командиру»: общих слов нет, хотя речь об одном и том же.
Векторный поиск сравнивает смысл, а не совпадение строк, и такие случаи закрывает.

Вторая часть задачи — не дать модели выдумывать. LLM охотно достраивает сюжетные
детали из своих общих знаний, и отличить их от настоящих невозможно. Поэтому ответ
собирается только из найденных фрагментов, а к нему прикладывается источник —
пользователь может проверить.

## Архитектура

```
raw_data_download.py  →  raw_data_handle.py  →  index_build.py  →  index_query.py  →  qf_bot.py
   загрузка               очистка и чанкинг      эмбеддинги          векторный поиск     интерфейс
   исходных данных                                и FAISS-индекс      top-k
```

**Индексация (офлайн):** документы загружаются, очищаются и режутся на чанки,
для каждого чанка считается эмбеддинг, векторы складываются в индекс FAISS.

**Запрос (онлайн):** вопрос переводится в вектор, по индексу ищутся k ближайших
чанков, найденное собирается в контекст и передаётся модели вместе с инструкцией
отвечать только по контексту.

## Стек

- Python
- **FAISS** — векторный индекс
- **sentence-transformers/all-MiniLM-L6-v2** — модель эмбеддингов (384 измерения)
- **Mistral 7B Instruct v0.2** в формате GGUF, квантизация Q6_K — генерация ответов локально

## Структура

| Путь | Назначение |
|---|---|
| `raw_data_download.py` | загрузка исходных документов |
| `raw_data_handle.py` | очистка, нормализация, разбиение на чанки |
| `index_build.py` | расчёт эмбеддингов и сборка FAISS-индекса |
| `index_query.py` | поиск по индексу, сборка контекста |
| `qf_bot.py` | интерфейс взаимодействия |
| `knowledge_base/` | подготовленный корпус |
| `raw_data/` | исходные документы |
| `faiss_index/` | сохранённый индекс |
| `etc/` | конфигурация |

## Запуск

```bash
pip install -r requirements.txt

python raw_data_download.py   # загрузить исходные данные
python raw_data_handle.py     # подготовить корпус
python index_build.py         # построить индекс
python qf_bot.py              # запустить бота
```

## Инженерные решения

**Чанкинг: 400 символов с перекрытием 50.** Короткие чанки дают более точный
векторный поиск — один фрагмент описывает одно событие, и его эмбеддинг не размывается
посторонним содержимым. Для материалов по сериалу это подходит: факты там плотные
и короткие, а не разложены на страницу рассуждений. Перекрытие в 50 символов страхует
от разрыва фразы на границе — без него фрагмент, попавший на стык, теряется для поиска целиком.

Цена такого выбора — узкий контекст: если ответ требует связать два удалённых
друг от друга факта, одного чанка не хватит, и всё зависит от того, попадут ли оба
в выдачу top-k.

**Размер выдачи (top-k).** Компромисс между полнотой контекста и бюджетом токенов:
больше чанков — выше шанс захватить нужный фрагмент, но выше стоимость запроса
и риск размыть внимание модели.

**Локальные модели вместо внешнего API.** `all-MiniLM-L6-v2` даёт компактные
384-мерные векторы — индекс занимает мало памяти, поиск быстрый, качество для
задачи достаточное. Mistral 7B в квантизации Q6_K помещается в память обычной
машины при небольшой потере качества против исходных весов. Вся обработка идёт
локально, поэтому документы не уходят наружу — для корпоративного корпуса это
часто определяющее требование.

**Разделение индексации и запроса.** Построение индекса вынесено в отдельный шаг,
поэтому переиндексация не блокирует работу поиска и может запускаться по расписанию.

## Ограничения и что изменилось бы в продакшене

Проект учебный, и часть решений сознательно упрощена:

- **FAISS — библиотека, а не хранилище.** Индекс живёт в памяти, без транзакций,
  прав доступа и фильтрации по метаданным. В продакшене взял бы `pgvector`:
  это обычный PostgreSQL, то есть готовые бэкапы, репликация, права и возможность
  искать по вектору одновременно с фильтром по метаданным в одном запросе.
- **Нет гибридного поиска.** Чисто векторный поиск промахивается, когда вопрос
  сформулирован не так, как документ. Связка вектор + BM25 закрывает этот случай.
- **Нет оценки качества.** Нужен набор эталонных вопросов с ожидаемыми источниками
  и метрика попадания, иначе изменения в чанкинге или модели нельзя сравнивать.
- **Нет инвалидации.** Обновление исходного документа требует полной переиндексации.
- **Нет прав доступа.** В корпоративной системе фильтрация по правам должна
  происходить до поиска, а не после — иначе утечка в выдаче.
- **Модель эмбеддингов заточена под английский.** `all-MiniLM-L6-v2` на других
  языках работает заметно хуже; под многоязычный корпус нужна модель вроде
  `multilingual-e5` или `LaBSE`.
